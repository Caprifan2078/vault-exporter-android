# TVA1 → Telegram Archive Viewer: проверяемый контракт формата

**Статус: спецификация текущего экспортёра, НЕ подтверждённая совместимость Viewer.**
Исходные нормативные файлы: `ChunkedVault.java`, `ArchiveWriter.java`,
`ArchiveVerifier.java`, `ExportEngine.java`.
Никогда не помещать настоящие архивы, пароли, API-ключи или личные переписки в CI.

## 1. Внешний поток: зашифрованный TVA1 (бинарный, не ZIP)

Все многобайтовые целые числа записаны в **big-endian**.

| Смещение | Размер | Значение |
| --- | ---: | --- |
| 0 | 4 | ASCII `TVA1` |
| 4 | 16 | Случайная соль PBKDF2 |
| 20 | 4 | Число итераций PBKDF2: **400000** |
| 24 | 4 | Размер plaintext-блока: **262144** байт |
| 28 | 8 | Случайный префикс nonce |

Пароль → `PBKDF2WithHmacSHA256`, соль из заголовка, 400000
итераций, 256 бит → ключ AES-256-GCM. Межъязыковую интерпретацию
символов пароля обязательно сверить на вымышленных тестовых архивах
с Unicode-паролем; не объявлять совместимость по теории.

После заголовка — последовательность блоков:
`int32 plaintextLength` (0…262144), ровно `plaintextLength` байт
AES-GCM ciphertext и 16 байт authentication tag.
Для блока с номером `sequence`, начиная с 0:
- `nonce = header[28..35] || uint32_be(sequence)` (12 байт);
- `AAD = header[0..35] || uint32_be(sequence) || 0x00` для данных;
- `AAD = header[0..35] || uint32_be(sequence) || 0x01` для конца;
- `plaintextLength=0` — **обязательный** аутентифицированный конец;
  никаких дополнительных байт после него.

Неверный пароль, tag, размер, последовательность, отсутствующий
конечный блок или хвостовой мусор — **отказ, без частичного импорта**.
Ограничивать длины до выделения памяти; не допускать переполнения
`sequence` и OOM при больших видео.

## 2. Расшифрованный поток: ZIP без отдельного файла на диске

Поток после AES-GCM — UTF-8 ZIP, записи идут **именно в этом порядке**:

Для каждой страницы `p` от 1 до `N`:

1. `messages/page-%06d.jsonl` — по одному исходному TDLib
   JSON-сообщению на строку, **ID строго убывают**, число записей
   на странице до 1000 по действующему verifier.
2. `media-index/page-%06d.jsonl` — ссылки на вложения этой страницы.
   Каждая запись содержит как минимум `message_id`, `file_id`,
   `bytes`, `sha256`, `path`. Также могут присутствовать
   `category`, `mime_type`, `original_name`, `role`, `position`.
3. Для каждого объекта media-index (в том же порядке):
   `media/<message_id>/<file_id>.<extension>` с точным SHA-256
   и точным числом байт из media-index. Один `message_id:file_id`
   не может встречаться дважды на странице.

После последней страницы:
- `participants.json` — массив JSON-объектов участников;
- `manifest.json` — **последняя** запись ZIP, schema `tg-vault-v1`,
  `chat_id`, `messages`, `media_downloaded`, `media_missing=0`,
  `history_end_reached=true`, `participants` и другие метаданные.

Verifier требует корректный порядок ZIP, уникальные media-reference
идентификаторы, корректный SHA/length, количество сообщений и медиа,
совпадение chat ID, строгий JSON без повторов ключей, отсутствие
неожиданных записей. Текущий verifier допускает часть старых
синтетических fixtures без chat_id, но **новый Viewer импорт должен
требовать chat_id у всех настоящих сообщений и в манифесте**.

## 3. Безопасный план импорта Viewer

1. `ACTION_OPEN_DOCUMENT` / SAF — явный выбор файла. Не выполнять
   автоимпорт и не принимать intent от неавторизованного внешнего приложения.
2. Получать пароль локально, хранить только на время операции, по
   возможности как `char[]` с занулением после использования; не
   сохранять в `Bundle`, `SharedPreferences`, crash logs, analytics.
3. Провести **полную проверку всего архива до импорта**
   (например, `ArchiveVerifier.verify` на первой итерации).
   После успешной проверки повторно открыть SAF-документ для потокового
   чтения. Между двумя проходами исходный документ может быть изменён:
   требуется проверить стабильную идентичность байт, либо сначала
   скопировать **только зашифрованный TVA1** в закрытый временный каталог.
4. Потоковое декодирование/ZIP: не сохранять расшифрованный полный ZIP
   или медиа во внешнее хранилище, системную галерею или открытый cache.
   При необходимости plaintext-индексировать в собственной БД Viewer
   **с включённым шифрованием на диске** и документированной политикой
   очистки. Предпросмотры медиа в буферах с ограниченным временем жизни.
5. При ошибке, прерывании, лимите памяти/места, неправильном пароле,
   отмене пользователем: не показывать частично импортированный чат,
   откатывать транзакцию, удалять временные расшифрованные файлы,
   сохранять исходный зашифрованный документ.
6. Для больших данных — проверять 1/10/100 тыс. сообщений, вложения,
   круглые видео, Opus, ZIP64, низкий объём памяти, `force-stop`,
   повторное открытие и неверный пароль. Покрыть Android 8–16;
   это **будущая** QA-приёмка, не пройденный тест.

## 4. Матрица совместимости и ограничения

- Экспортёр: **создание и проверка** TVA1 пройдены на вымышленных
  данных; полный live Telegram E2E отсутствует.
- Viewer: **импорт TVA1 пока не реализован/не проверен**. Этот файл
  не заменяет его код, тесты или APK.
- Cryptography format TVA1 и schema tg-vault-v1 — разные версии.
  Несовместимое изменение формата требует новой версии/явной миграции;
  не нужно «угадывать» неизвестные поля или отключать валидацию.
- Не путать целостность собственного архива с полнотой Telegram:
  удалённые/защищённые сообщения, изменения во время выгрузки
  и недоступные серверные данные не восстановить.
